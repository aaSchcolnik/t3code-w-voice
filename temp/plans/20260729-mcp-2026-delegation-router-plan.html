T3 Code · implementation plan · 2026-07-29

MCP 2026 and provider-neutral delegation

Keep MCP as T3 Code’s agent-facing control plane, keep the existing delegated-run runtime, and add a deterministic provider-neutral router above it. The parent agent decomposes work; T3 Code selects eligible provider instances and models, records why, and preserves legacy provider behavior while adopting stable MCP 2026.

01

Decision

The pivot is architectural, not a protocol replacement: preserve the working execution core and remove provider choice from prompt choreography.

Decision

MCP stays. It is already the cross-provider control plane for typed tools, scoped authorization, remote access, and project context. Provider CLIs remain execution adapters; no T3 CLI is needed.

Scope

Ship three independent tracks: provider-neutral delegation, progressive skill/knowledge discovery, and MCP 2026 compatibility. The router does not wait for the protocol migration. MCP Tasks remains an optional fourth projection.

Unified router over existing runs
The parent supplies bounded lanes. A deterministic server policy selects and records provider/model assignments, then launches through DelegatedRunService.
Chosen
Replace MCP with a CLI
Would recreate authentication, discovery, remote transport, schemas, and lifecycle while leaving provider selection unsolved.
Rejected
Use another LLM as router
Adds cost, latency, nondeterminism, and another failure dependency before a measurable deterministic baseline exists.
Deferred

04

Delegation router

The parent remains responsible for semantic decomposition and synthesis. The server owns eligibility, provider/model selection, admission, diversity, and an auditable explanation. 

// Parent describes independent tasks; it does not choose a provider.
delegate_start({
  tasks: [
    { laneId: "protocol", role: "scout", task: "Verify migration semantics" },
    { laneId: "runtime", role: "scout", task: "Audit restart and fallback safety" }
  ]
})
Stage Rule Persisted evidence
1 · resolve Skill override → workflow override → project/global role chain → defaults policy source, role, policy version
2 · filter Availability, model, attachments, questions, resume, recursion stable rejection reason codes
3 · select First eligible target in configured order; no invented cross-provider score chain position and exact target
4 · diversify When preferred, choose the first eligible unused provider without overriding constraints diversity policy and assignment
5 · reserve Batch capacity and idempotency are atomic before any child starts repository revision and workflow ID
6 · dispatch Fallback only before acknowledged turn acceptance attempt, fallback source, dispatch state
Proactive

Proactive mode means the main agent is instructed to notice independent lanes and call the router. It does not mean the server secretly spawns work before the agent has decomposed it.

Canonical tools

  • delegate_start — jointly route and reserve one to four bounded tasks.
  • delegate_cancel — cancel a batch or child with ownership checks.
  • delegate_respond — answer provider-neutral pending input.
  • delegate_capabilities — optional read-only diagnostics for settings and route explanations.

Implementation chunks

Three independently shippable tracks are split into reviewable chunks: delegation/router, progressive knowledge, and protocol compatibility. Tasks stays behind a separate optional gate.

0 · Protocol harness

foundation

Pin stable conformance fixtures and verify all five provider clients. Decide Effect upgrade versus the narrow official-SDK v2 modern handler.

  • mcp/protocol/McpProtocolProfile.ts
  • Effect dependency, patch, and vendored subtree gate

1–3 · Contracts, capabilities, pure router

track A

Add backward-compatible schemas, adapter-declared delegation capabilities, configured ordered-chain selection, and a versioned evaluation corpus.

  • packages/contracts/src/delegationRouter.ts
  • provider/DelegationRouter.ts
  • provider/fixtures/delegation-routing-cases.json

4–5 · Repository and safe dispatch

track A

Put the versioned JSON aggregate behind a repository, add idempotency and atomic admission, then split session/turn acceptance so fallback has a provable boundary.

  • orchestration/DelegatedRunRepository.ts
  • orchestration/DelegatedRunService.ts

6–7 · Coordinator and unified tools

track A outcome

Jointly route one to four tasks, atomically preflight them, launch persisted siblings independently, and expose provider-neutral lifecycle tools.

  • DelegationCoordinator.ts
  • mcp/toolkits/delegationRouter/

8 · One-endpoint MCP 2026 gateway

track B

Independently route legacy requests to the sessionful Effect handler and modern requests to strict SDK v2 serving on the same /mcp URL.

8B · Tasks extension

optional gate

Only after extension maturity and real provider-client support: map one delegation batch to one Task and persist exactly one delivery mode—Task result or parent wake. Never make this a routing prerequisite.

9 · Compact skills and knowledge

track C

Independently add capability-filtered catalogs, search, and bounded hydration. Inject policy only through legitimate system/developer channels; document adapters without one.

10–11 · Web/desktop and mobile

multi-surface

Configure global/project policy, explain routes in existing subagent views, then add mobile observation before mobile configuration.

12 · Shadow evaluation and rollout

release gate

Measure decisions without launching, then move through suggested and opt-in proactive behavior. Default proactive remains a later metrics-gated decision.

The proof strategy is focused: pure policy fixtures first, then lifecycle races and protocol conformance, then one integrated pass per client surface.

Bed Primary files Must prove
Contracts settings.test.ts, delegatedRun.test.ts, subagent.test.ts Old persisted settings/runs decode; optional route metadata round-trips

Evaluation corpus requirements

  • Research, planning, implementation, debugging, tests, review, docs, knowledge scans.
  • Attachments, structured input, read-only and workspace-write requirements.
  • One provider, multiple providers, multiple instances of one driver, and unavailable models.
  • Explicit provider constraints and delegated-child recursion attempts.
  • Assert selection and rejection invariants; avoid brittle snapshots of incidental totals.
08

Risks and invariants

The dangerous failures are duplicate work, unsafe replay, hidden constraint violations, and inconsistent state across provider and client boundaries.

Severity Risk Invariant / mitigation
High Provider accepted a turn but T3 retries elsewhere No fallback after acknowledged or ambiguous dispatch; never replay task text on restart
High Concurrent starts exceed four-run limit Reserve batch and environment capacity atomically before launch
High Task/run accessed by another thread Ownership is environment + parent thread and survives only same-owner bearer rotation
Medium Provider diversity violates intended priority Choose only among eligible configured candidates; never override hard constraints or disabled providers
Medium Catalog advertises tools the session cannot call Request-scoped listing plus unchanged call-time authorization
Medium Final-looking text appears while run is active Only provider lifecycle events set terminal state
Medium Settings change after bearer issuance Router reloads effective global/project policy at call time
Low Tasks extension is not ready Keep it optional; parent wake and normalized streams remain primary
Observed

The Kimi K3 run failed at provider startup, and the Claude planning run returned only an opening status line. Those are not missing footnotes—they are evidence that launch acknowledgement, terminal truth, fallback safety, and result completeness need explicit contracts.

  • No recursive routed delegation; use explicit session kind instead of a thread-name prefix.
  • No silent violation of explicit provider/model constraints.
  • No invisible partial batch.
  • No reinterpretation of a persisted route under a newer policy.
  • No fake token budget where usage correlation is incomplete.
  • No permanent dual implementation; legacy removal has measured gates.
09

Rollout and sources

Ship the deterministic foundation first, observe it in shadow mode, and only then increase the parent agent’s proactive behavior or retire compatibility tools.

Shadow

no launches

Compute decisions against the corpus and live eligible requests. Measure exclusion reasons, candidate spread, and user constraints without changing execution.

Suggested

first release

Expose delegate_start. Keep provider-specific tools available as compatibility aliases.

Opt-in proactive

agent prompted

Inject the compact decomposition heuristic. The parent calls the router; the server still never spawns secretly.

Default proactive

later decision

Consider only after route success, cancellation, fallback, diversity, and override rates meet published thresholds.

Deprecation

measured adoption

Retire provider-specific start tools and the legacy MCP branch separately. Enable Tasks only through its own extension gate.
